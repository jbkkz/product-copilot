# Epic: Event Check-in & Freelancer Reconciliation

> Delivery epic — generated by Product Copilot

**Milestone:** Pilot

**Goal:** Give door staff a live, offline-reliable view of guest approval status at check-in, and give finance a traceable, reconciled link between freelancer engagement, contracts and invoices for this event — closing both the door and the back-office gap in six weeks.

**Business value:** Removes the two costliest failure points in running this event: wrongful admissions/rejections in front of the client on the day, and weeks of manual invoice-vs-hours reconciliation afterward. Both are visible, recurring pain the client named explicitly.

## In scope

- Offline-capable check-in app with local attendee snapshot and later sync
- Live approval-status display for door staff, with a defined outcome for duplicate/re-entry scans
- Manual fallback: fuzzy name search and on-the-spot registration for walk-ins/unmatched attendees
- Alerting on attendee approval mismatches, routed to a defined owner
- Signed-contract gate for freelancers working the door
- Post-event reconciliation report linking check-ins, freelancer engagement and invoiced amounts
- Audit trail across check-in, engagement and invoicing data
- Role-based permissions for door staff, event manager and finance
- On-site rehearsal and throughput testing of the check-in flow before go-live

## Out of scope

- Real-time (in-event) alerting on freelancer hours-vs-invoice mismatches — deferred to the post-event report pending legal review
- A reusable multi-event configuration kit — this build targets the single event; generalisation is a future opportunity
- Any new invoicing engine or contract-management system — this epic reconciles against whatever contract/invoice source is confirmed, it does not replace it
- Badge design, zone/session access modelling beyond basic approval status

## Issues

### [ ] #1 — Spike: split the 'mismatch' concept into attendee-approval and freelancer-billing rule sets

**Labels:** `spike`

Define, separately, what makes a guest 'approved', what constitutes an attendee check-in mismatch, and what constitutes a freelancer hours/contract/invoice mismatch — each with its own owner and channel. This unblocks all downstream workflow and alerting work; do not build a single undifferentiated alert.

### [ ] #2 — Spike: confirm the basis for freelancer reconciliation (deliverable/mission terms, not clocked hours)

**Labels:** `spike`

Check with legal/HR whether clocking freelancer arrival/departure and driving invoice comparison from hours worked creates disguised-employment risk under French labor law; confirm the reconciliation should instead compare invoiced amounts against mission/deliverable terms in the signed contract.

### [ ] #3 — Spike: identify source of truth for freelancer contracts, rates and signature status

**Labels:** `spike`, `integration`

Determine whether freelancer contracts/rates already exist in another system (e.g. an HR/contract platform) requiring integration, or must be entered fresh for this event; this decides whether the freelancer side is an integration or a data-entry build.

### [ ] #4 — Build attendee and approval-status data model

**Labels:** `backend`, `feature` · **Depends on:** #1

Model Attendee, Category and Approval status, sourced per the rules defined in #1. Include support for late additions (walk-ins, substitutions, name corrections) since the list is not final until the event.

### [ ] #5 — Build offline check-in engine: local snapshot + sync

**Labels:** `backend`, `feature` · **Depends on:** #4

Each door device holds a local snapshot of the approval list and records check-ins offline; check-ins sync back with conflict resolution and a visible pending state when connectivity returns. Follows the decided offline-first architecture given the venue's unusable wifi — do not build an online-only path.

### [ ] #6 — Handle duplicate, re-entry and multi-door concurrency at check-in

**Labels:** `backend`, `feature` · **Depends on:** #5

Define and implement the outcome when the same attendee is scanned twice within seconds across independent devices, and distinguish a genuine duplicate from a re-entry or a different zone/session. Assumes a single check-in per attendee for this event unless zones are confirmed in scope.

### [ ] #7 — Build door-staff check-in UI: live status, fuzzy search, on-the-spot registration

**Labels:** `frontend`, `feature` · **Depends on:** #5

Show live approval status per attendee; when a scan or name match fails, provide fuzzy name search and an on-site registration path. UI must be usable by a first-time operator in poor light and one-handed, and support the required throughput.

### [ ] #8 — Build attendee approval-mismatch alerting

**Labels:** `backend`, `feature` · **Depends on:** #1, #7

Fire an alert to the owner defined in #1 when a check-in doesn't resolve cleanly against the approval list; keep this alert scoped to attendee approval only, separate from any freelancer-billing signal.

### [ ] #9 — Add signed-contract gate for freelancer door staff

**Labels:** `backend`, `permissions` · **Depends on:** #1, #3

Prevent, or explicitly flag, a freelancer with an unsigned contract from operating the check-in app on the day, per the rule confirmed in #1. Exact enforcement (hard block vs. flagged warning) should follow the client's decision, not be assumed.

### [ ] #10 — Build freelancer engagement and mission/contract data model

**Labels:** `backend`, `feature` · **Depends on:** #2, #3

Model Freelancer, Mission, Contract and engagement records for the event, pulling contract/rate data from the source confirmed in #3 rather than re-entering it, per the reconciliation basis confirmed in #2.

### [ ] #11 — Build post-event reconciliation report (engagement vs. contract vs. invoice)

**Labels:** `backend`, `feature` · **Depends on:** #10

Produce a report linking each freelancer's mission engagement, contract terms and invoiced amount, flagging discrepancies for finance to review at close. Ships as an asynchronous post-event report, not a live in-event alert, per the sequencing decision to protect check-in rehearsal time.

### [ ] #12 — Add audit trail across check-in and reconciliation data

**Labels:** `backend`, `qa` · **Depends on:** #8, #11

Record who did what and when across check-ins, approval status changes, contract-gate decisions and reconciliation flags, so finance's reconciliation is traceable end to end and not just a snapshot report.

### [ ] #13 — Configure role-based permissions for door staff, event manager and finance

**Labels:** `permissions`, `config` · **Depends on:** #1, #8, #11

Door staff get read-only access to approval status; the alert owner (event manager, tbc) can act on mismatches; finance gets the reconciliation report view. Exact split to be confirmed against #1.

### [ ] #14 — Rehearse check-in flow on real devices at the venue

**Labels:** `qa` · **Depends on:** #6, #7, #9

Run a full-throughput rehearsal on the actual devices and venue network conditions before go-live, validating offline snapshot freshness, sync behaviour and duplicate handling under real connectivity. This is the highest-risk path in the build and gets priority rehearsal time over the reconciliation report.

### [ ] #15 — Define and run acceptance scenarios for check-in and reconciliation

**Labels:** `qa` · **Depends on:** #14, #11

Validate: a rehearsal check-in matching against the offline approval list, a mismatch alert firing and reaching its owner, an unsigned-contract freelancer being handled per the rule in #9, and a reconciliation report finance confirms ties out cleanly.

## Open questions

- Who exactly receives an attendee-approval mismatch alert — the event manager, security, or someone else — and via which channel?
- Is this event a one-off build or the first instance of a reusable event kit? This affects how much configurability effort is worth investing given the six-week deadline.
- What is the precise definition of 'reconciles cleanly' for finance — full invoice approval before payment, or a discrepancy report they review manually?
- Are zones or sessions in scope for this event, or is a single check-in per attendee sufficient?
