# Epic: Traceable Leave Approval Workflow

> Delivery epic — generated by Requivo

**Milestone:** Pilot

**Goal:** Replace the informal, email-based leave approval process with a system where every leave request reaches an explicit, recorded decision — enforcing HR sign-off for long or over-balance requests and producing a full audit trail.

**Business value:** Eliminates the recurring payroll surprise of unapproved leave and the compliance exposure of undocumented decisions; gives HR and the works council a defensible audit trail while keeping routine approvals fast.

## In scope

- Leave/Absence request lifecycle: submitted → manager review → HR review (mandatory above 10 days or over-balance) → approved/rejected
- Manager delegation to a named substitute for a date range
- 3-working-day stall detection and auto-escalation to HR
- Cancellation flow with automatic same-night balance restoration
- Nightly bidirectional sync with the legacy HR tool (balances, approvals, cancellations write-back)
- Mismatch handling: requests during an unresolved sync mismatch proceed flagged at-risk, never blocked
- Full audit trail (who approved/overrode/escalated/cancelled, when), retained 5 years
- Reporting-line-based permissions and HR override rights
- Single shared rule set for the pilot (no per-department/country configuration)

## Out of scope

- Per-department / per-country rule configuration
- Migrating balance ownership off the legacy HR tool (post-pilot decision)
- Generalizing the approval+delegation+escalation logic into a reusable cross-module circuit (noted as a future opportunity)
- Platform-level compliance/audit-trail service reused by other modules (future opportunity)
- Organizational enforcement against email-based approvals (policy/communication lever, not a build item)

## Issues

### [ ] #1 — Resolve the zero-mismatch metric vs. nightly-sync design conflict

**Labels:** `spike`

The pilot's success bar of 'zero unresolved balance mismatches at month end' assumes a level of accuracy the nightly (not real-time) sync design doesn't guarantee. Decide with the client whether the metric should be reworded as 'resolved within 24h' or whether over-balance checks need a live call to the legacy tool, before this is baked into acceptance testing.

### [ ] #2 — Model the Leave/Absence request entity

**Labels:** `backend`, `feature`

Build the Leave/Absence data model (employee, dates, duration, status, approver chain, balance reference, over-balance flag, at-risk flag). Field-level detail beyond what the workflow needs was inferred, not itemized by the client — confirm before finalizing the schema.

### [ ] #3 — Build the core request lifecycle state machine

**Labels:** `backend`, `feature` · **Depends on:** #2

Implement states submitted → manager review → HR review → approved/rejected, with cancellation as a parallel transition. This is the backbone every other rule (HR sign-off, escalation, cancellation) plugs into.

### [ ] #4 — Implement manager approval and named-substitute delegation

**Labels:** `backend`, `feature`, `permissions` · **Depends on:** #3

Manager approves by default following the reporting line; support delegating approval authority to a named substitute for a specific date range.

### [ ] #5 — Implement mandatory HR sign-off for long/over-balance requests

**Labels:** `backend`, `feature` · **Depends on:** #3

Route to HR review whenever duration exceeds 10 working days or the request exceeds available balance; over-balance requests are allowed but must be flagged and cannot be manager-approved alone. Include HR override authority over any decision.

### [ ] #6 — Add stall detection and auto-escalation to HR

**Labels:** `backend`, `feature` · **Depends on:** #3, #5

If a request has no named backup approver and sits unresolved for 3 working days, auto-escalate it to HR so no request stalls silently.

### [ ] #7 — Implement cancellation with automatic balance restoration

**Labels:** `backend`, `feature` · **Depends on:** #3

Allow cancellation while submitted, or up to 48h before start if already approved; restore balance automatically the same night without requiring HR confirmation.

### [ ] #8 — Build nightly bidirectional sync with the legacy HR tool

**Labels:** `integration`, `backend` · **Depends on:** #2

Sync balances from the legacy tool (source of truth during the pilot) and write back approvals/cancellations the same night. Treat this as the pilot's dual-system dependency — an explicit post-pilot direction for balance ownership is still open.

### [ ] #9 — Handle balance mismatches without blocking requests

**Labels:** `backend`, `feature` · **Depends on:** #8, #1

When the nightly sync surfaces a disagreement, queue it for HR resolution the next morning; new requests submitted during that window proceed against the last-known balance and are flagged at-risk rather than blocked.

### [ ] #10 — Build the audit trail

**Labels:** `backend`, `feature`, `qa` · **Depends on:** #4, #5, #6, #7

Log every approval, override, escalation and cancellation with actor and timestamp, retained 5 years for works-council compliance. Must cover at-risk and mismatch-window decisions, not just the happy path.

### [ ] #11 — Configure permissions for approval, override and delegation

**Labels:** `permissions`, `backend` · **Depends on:** #4, #5

Approval rights follow the reporting line; HR can override any decision; a manager can delegate to a named substitute for a bounded date range. Verify these rules hold consistently across the manager and HR review states.

### [ ] #12 — Build audit trail reporting and export

**Labels:** `frontend`, `backend`, `qa` · **Depends on:** #10

Provide a view/export of the audit trail sufficient for works-council and internal review, including turnaround time and mismatch/at-risk resolution tracking against the pilot's success metrics.

### [ ] #13 — Run end-to-end acceptance testing against pilot success criteria

**Labels:** `qa` · **Depends on:** #6, #7, #9, #11, #12

Validate: 100% of requests reach a recorded decision, no silent drops; mismatches resolved per the agreed metric wording; median turnaround under 2 working days; full manager adoption in-app; audit trail complete for a sample including at-risk and cancellation cases.

## Open questions

- What organizational lever (policy, payroll gate, HR spot-check) will ensure managers actually stop approving leave by email, since the workflow alone can't enforce that behavior change?
- Is the legacy HR tool meant to remain the permanent balance source of truth after the pilot, or should balance ownership migrate into this platform — this shapes whether the nightly-sync/mismatch design is temporary or permanent?
- Should the pilot's 'zero unresolved mismatches at month end' metric be reworded to match the async nightly-sync design (e.g. 'resolved within 24h'), or should over-balance checks call the legacy tool live instead?
