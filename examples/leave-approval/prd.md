# Leave Request Approval Workflow — Traceable Decision Engine

> Product Requirements Document — generated by Requivo

## Summary

This project replaces the current email-based leave approval process with a structured workflow in which every leave request reaches an explicit, recorded decision. It enforces mandatory HR sign-off for long or over-balance requests, keeps the process moving even when balance data is temporarily unreliable, and produces a full audit trail for works-council compliance. The goal is not a nicer request form but a process that never silently fails to produce a decision.

## Problem

Leave requests are currently approved informally by email: messages get lost or go unanswered for weeks, employees sometimes take leave that was never formally approved, and HR only discovers the gap at payroll. The underlying need is a decision process that is always traceable and always concludes — not a better-looking request form.

## Goals

- Every leave request reaches an explicit, recorded decision — no request is silently dropped
- No unresolved balance mismatches persist beyond a defined resolution window
- Median approval turnaround under 2 working days
- Full manager adoption of the platform for approvals, with no approvals happening by email in the pilot scope
- A complete, retrievable audit trail for every decision, override, escalation and cancellation

## Users & roles

- Employee — submits and can cancel their own leave requests
- Manager — default approver within the reporting line, can delegate to a named substitute for a date range
- HR — mandatory sign-off above 10 working days or for over-balance requests, override authority, escalation target, resolves nightly balance mismatches
- Works council — external compliance stakeholder relying on the audit trail
- Legacy HR tool — system of record for leave balances during the pilot

## Scope

**In scope**

- Leave/Absence request lifecycle: submitted → manager review → HR review (when required) → approved/rejected/cancelled
- Mandatory HR sign-off for requests over 10 working days or exceeding available balance
- Manager delegation to a named substitute approver for a specific date range
- Automatic escalation to HR after 3 working days with no named backup approver
- Employee-initiated cancellation while submitted, or up to 48 hours before start if already approved, with automatic same-night balance restoration
- Nightly bidirectional sync with the legacy HR tool as the balance source of truth, with same-night write-back of approvals and cancellations
- Handling of requests submitted during an unresolved balance mismatch: processed against last-known balance, flagged at-risk, never blocked
- Full audit trail of who approved, overrode, escalated or cancelled each request and when, retained for 5 years
- A single shared workflow and rule set for the pilot (no per-department or per-country variation)

**Out of scope**

- Per-department or per-country configuration of rules or workflow (deferred past pilot)
- Generalizing the approval/delegation/escalation engine into a reusable circuit for other modules (noted as a future opportunity, not part of this build)
- Building the audit trail as a platform-wide compliance service beyond this module (future opportunity)
- Extracting the nightly-sync/mismatch pattern into a reusable legacy-integration module (future opportunity)
- Migrating balance ownership off the legacy HR tool (decision deferred to post-pilot)

## Workflow

1. Employee submits a leave request
2. Request enters manager review by default
3. If duration > 10 working days or request exceeds available balance → request routes to mandatory HR review (over-balance also requires explicit HR confirmation)
4. If no named backup approver responds within 3 working days → request auto-escalates to HR
5. Manager (or delegated substitute) or HR approves or rejects the request
6. Approved/rejected/cancelled decision is written back to the legacy HR tool the same night
7. Employee may cancel while submitted, or up to 48 hours before start if approved — balance restored automatically the same night
8. Nightly sync compares balances with the legacy tool; discrepancies raise a mismatch queued for HR resolution the next morning
9. Requests submitted during an open mismatch proceed against last-known balance, flagged at-risk, pending HR reconciliation

## Business rules

- Manager is the default approver for standard requests
- HR sign-off is mandatory when duration exceeds 10 working days or when the request exceeds available balance
- Over-balance requests are allowed but flagged and require explicit HR confirmation — they cannot be manager-approved alone
- Cancellations automatically restore balance the same night without requiring HR confirmation
- A manager may delegate approval authority to a named substitute for a defined date range
- A single shared rule set applies across the pilot; no per-department or per-country variation is built at this stage

## Permissions

- Employee: can create and cancel their own leave requests
- Manager: can approve/reject requests within their reporting line, and delegate approval to a named substitute for a date range
- HR: mandatory sign-off authority above thresholds, override authority on any decision, resolves nightly balance mismatches
- Works council: relies on the audit trail for compliance (exact access level not yet defined — see open questions)

## Integrations & notifications

- Legacy HR tool: remains the source of truth for leave balances during the pilot, via nightly bidirectional sync
- Approvals and cancellations write back to the legacy tool the same night
- Balance disagreements from the sync raise a mismatch queued for HR review the following morning

## Edge cases

- Over-balance request: allowed, flagged, requires HR confirmation before final approval
- Request submitted during an unresolved balance mismatch: processed against last-known balance, flagged at-risk, never blocked
- Cancellation after approval: automatic same-night balance restoration, no HR confirmation required
- No named backup approver and request stalls 3 working days: auto-escalates to HR

## Acceptance criteria

- [ ] 100% of submitted leave requests reach an explicit, recorded decision (approved, rejected, or cancelled) — none are silently dropped
- [ ] No balance mismatch remains unresolved beyond the agreed resolution window (see open question on the exact target, given nightly sync is asynchronous by design)
- [ ] Median approval turnaround is under 2 working days across the pilot
- [ ] All manager approvals in the pilot scope occur through the platform, with no approvals recorded as having happened by email
- [ ] The audit trail for a sample of requests — including at-risk and cancelled cases — shows a complete, correctly attributed history of actions and timestamps

## Assumptions

- Formal acceptance test scenarios will be built from the stated success metrics, even though the client has not yet phrased them as test cases
- GDPR and French labor-law obligations apply to this HR data as standard practice, beyond the explicitly named works-council retention requirement
- The Leave/Absence request's detailed field list follows the platform's standard model; only the fields needed to support the workflow (dates, duration, status, approver chain, balance reference, flags) have been confirmed so far
- A single shared workflow/rule set (no per-department or per-country configuration) is acceptable for the pilot, per the client's stated scope decision

## Open questions

- The 'zero unresolved mismatches at month end' success metric appears to conflict with the nightly (asynchronous) sync design, which allows mismatches to occur and persist until HR reconciles them each morning — should the metric be reworded (e.g. 'resolved within 24 hours'), or should over-balance checks call the legacy tool live instead of relying on the nightly batch?
- Nothing in the current scope technically prevents a manager from approving by email as before — what organizational policy or lever (e.g. payroll only accepting system-recorded decisions) will make the platform the enforced approval channel, and should this be added to acceptance criteria?
- The legacy HR tool is described as authoritative 'during the pilot' — what is the intended post-pilot state: migrate balance ownership into the new platform, or continue the nightly-sync dual-system dependency indefinitely?
- The audit trail is a confirmed requirement, but its presentation (dashboard, exportable report, raw log access) has not been defined — what format does HR/works council need?
- What level of access does the works council require — read-only visibility into the audit trail, periodic exports, or something else?

## Risks

- Adoption risk: the system only solves the underlying problem if managers genuinely stop approving by email — a functionally correct workflow that gets routed around would silently reproduce the original problem while passing every functional test
- The at-risk flag on mismatch-window requests could be ignored or mismanaged by HR during the morning reconciliation, undermining the 'zero mismatch' goal
- The success metric and the async sync design may be structurally inconsistent, risking a pilot that is judged to have failed even when the system behaves as designed
- Treating the legacy tool's authority as temporary without a decided migration path risks the pilot's dual-system architecture becoming permanent by default
