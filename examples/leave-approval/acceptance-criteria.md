# Leave Request Approval — Acceptance Criteria (Pilot)

> Acceptance criteria — generated by Requivo

## Standard leave request & manager approval

### [ ] AC-1 — Employee submits a routine request and manager approves it  _Happy path_

- **Given** Employee has sufficient balance
- **And** Requested duration is 10 working days or less
- **When** Employee submits the leave request and their manager approves it
- **Then** Request status moves to approved
- **And** No HR review step is triggered
- **And** The decision (approver, timestamp) is recorded against the request

### [ ] AC-2 — Manager rejects a routine request  _Happy path_

- **Given** A submitted request within balance and 10 days or less
- **When** Manager rejects the request
- **Then** Request status moves to rejected, not left pending
- **And** The rejection is recorded with who rejected and when
- **And** Employee's balance is unaffected

## Mandatory HR sign-off for long or over-balance requests

### [ ] AC-3 — Request over 10 working days requires HR sign-off  _Happy path_

- **Given** Requested duration is more than 10 working days
- **When** Manager approves the request
- **Then** Request does not become final on manager approval alone
- **And** Request routes to HR for sign-off
- **And** Final status (approved/rejected) is only set once HR has decided

### [ ] AC-4 — Over-balance request requires HR confirmation  _Happy path_

- **Given** Requested duration exceeds the employee's available balance
- **When** Employee submits the request
- **Then** Request is flagged as over-balance
- **And** Request cannot reach approved status from manager action alone
- **And** Request is only approved once HR has explicitly confirmed it

### [ ] AC-5 — Boundary check: exactly 10 working days stays manager-only  _Edge case_

- **Given** Requested duration is exactly 10 working days
- **And** Request is within balance
- **When** Manager approves the request
- **Then** Request is finalised on manager approval alone, without routing to HR

## Delegation and no-response escalation

### [ ] AC-6 — Manager delegates approval to a named substitute for a date range  _Happy path_

- **Given** Manager has set a named substitute for a specific date range
- **And** A request falls within that range
- **When** The substitute approves the request
- **Then** The approval is accepted as valid
- **And** The audit trail records the substitute as the acting approver

### [ ] AC-7 — Stalled request with no substitute auto-escalates to HR  _Edge case_

- **Given** A request has no named substitute available
- **And** 3 working days have passed with no manager decision
- **When** The 3-working-day stall threshold is reached
- **Then** The request automatically escalates to HR
- **And** The request never remains indefinitely pending
- **And** The escalation event is recorded in the audit trail

## Cancellation and balance restoration

### [ ] AC-8 — Employee cancels a request still awaiting a decision  _Happy path_

- **Given** Request status is submitted (not yet approved)
- **When** Employee cancels the request
- **Then** Request status becomes cancelled
- **And** No HR confirmation is required for the cancellation

### [ ] AC-9 — Employee cancels an approved request more than 48h before start  _Happy path_

- **Given** Request is approved
- **And** Cancellation happens more than 48h before the leave start date
- **When** Employee cancels the request
- **Then** Request status becomes cancelled
- **And** Balance is automatically restored the same night
- **And** No HR confirmation is required

### [ ] AC-10 — Cancellation attempted inside the 48h cutoff  _Edge case_

- **Given** Request is approved
- **And** Less than 48h remain before the leave start date
- **When** Employee attempts to cancel the request
- **Then** The system's handling of this case (blocked vs. still allowed) should be verified against the agreed rule before sign-off, as the exact cutoff behaviour is not yet confirmed

## Legacy balance sync and mismatch handling

### [ ] AC-11 — Nightly sync writes back approvals and cancellations  _Happy path_

- **Given** One or more requests were approved or cancelled during the day
- **When** The nightly sync with the legacy HR tool runs
- **Then** All same-day approvals and cancellations are reflected in the legacy tool after that night's sync
- **And** No approved or cancelled request is missing from the sync batch

### [ ] AC-12 — New request submitted while a balance mismatch is unresolved  _Edge case_

- **Given** A balance mismatch between the platform and the legacy tool has been flagged and is not yet resolved
- **When** An employee submits a new leave request during this window
- **Then** The request is processed against the last-known balance rather than blocked
- **And** The request is flagged as at-risk
- **And** The request still reaches manager/HR review as normal

### [ ] AC-13 — HR resolves a flagged mismatch  _Happy path_

- **Given** A mismatch was raised overnight and queued for HR
- **When** HR reviews and resolves the mismatch the next morning
- **Then** The mismatch is cleared from the queue
- **And** Any at-risk requests tied to it can be reconciled against the confirmed balance

## Permission boundaries

### [ ] AC-14 — HR can override any decision  _Permission_

- **Given** A request has an existing manager or HR decision
- **When** HR overrides the decision
- **Then** The new decision takes effect and is recorded as an HR override
- **And** The prior decision remains visible in the audit history rather than being erased

### [ ] AC-15 — Manager alone cannot finalise an over-balance or >10-day request  _Permission_

- **Given** A request is over-balance or exceeds 10 working days
- **When** Manager attempts to approve the request without HR sign-off
- **Then** The request cannot reach a final approved status from the manager's action alone
- **And** The system indicates HR sign-off is still pending

### [ ] AC-16 — Employee cannot approve their own request  _Permission_

- **Given** An employee has submitted a leave request
- **When** The employee attempts to approve or reject their own request
- **Then** The action is blocked
- **And** Only the manager, an authorised substitute, or HR can record a decision on the request

### [ ] AC-17 — Substitute approver acts only within their delegated date range  _Permission_

- **Given** A substitute is delegated approval rights for a specific date range only
- **When** The substitute attempts to act on a request falling outside that date range
- **Then** The expected behaviour (blocked vs. allowed) should be confirmed, as delegation scope beyond the date range is not explicitly defined

## Audit trail and compliance reporting

### [ ] AC-18 — Every decision type is captured in the audit trail  _Happy path_

- **Given** A sample set of requests including approvals, rejections, overrides, escalations and cancellations
- **When** Each request's history is reviewed
- **Then** Each decision shows who acted, what action was taken, and when
- **And** At-risk (mismatch-window) requests and cancellations both appear in the trail with their status changes
- **And** No request in the sample is missing a recorded decision

### [ ] AC-19 — No request is left without a final recorded decision  _Edge case_

- **Given** A batch of requests submitted during the pilot period
- **When** The batch is reviewed at month end
- **Then** 100% of requests show an explicit final status (approved, rejected or cancelled) — none left silently pending

## Pilot success measures

### [ ] AC-20 — Approval turnaround is measured against the pilot target  _Edge case_

- **Given** A representative sample of requests processed during the pilot
- **When** Turnaround time from submission to final decision is measured
- **Then** The expected median turnaround of under 2 working days should be checked against actual pilot data before sign-off, since this has not yet been validated as a hard pass/fail gate

## Open questions

- The success metric 'zero unresolved balance mismatches at month end' appears to conflict with the accepted design where mismatches occur nightly and are only resolved the next morning — should the metric instead be 'resolved within 24h', or should over-balance checks call the legacy tool live instead of relying on the nightly batch? This needs resolving before it can be tested as a pass/fail gate.
- Nothing in the current scope stops a manager from continuing to approve leave by email outside the platform. Is there a planned organizational/policy lever (e.g. payroll only accepting system-recorded decisions) that should be part of acceptance testing, or is enforcement considered out of scope for the pilot?
- The legacy HR tool is described as authoritative 'during the pilot' — is there a defined plan for balance ownership after the pilot (migrate to the new platform vs. keep the nightly-sync dependency permanently)? This affects whether the mismatch-handling design should be tested as a permanent behaviour or a temporary workaround.
- Cancellation behaviour when attempted inside the 48h cutoff before an approved leave's start date is not explicitly defined — is it blocked, allowed with a warning, or routed to HR?
- Delegation scope for a substitute approver outside their assigned date range is not explicitly defined — should out-of-range actions be blocked?
- The detailed field-level structure of the Leave/Absence record (beyond what the workflow implies) has not been itemized — worth confirming before building detailed data-validation tests, though it does not block core workflow testing.
